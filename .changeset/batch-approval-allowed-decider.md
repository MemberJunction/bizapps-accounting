Security: a journal entry batch is sent only on an approval from an allowed decider (bc-aidp-next-golive#320 §3). `TasksAppApprovalGate.assertApproved` used to accept any Approved decision on the batch's approval Task, so a decision saved straight into the tasks app (the Tasks inbox, or anyone allowed to create a Task Decision) counted. It now counts a decision only when it is attributed to a Person bound to the company's Approval CFO and not to the batch's builder; a decision with no Person counts only when the batch's approval audit names the Approval CFO. A refused send says which of these failed: no Approval CFO configured, the Approval CFO built the batch, the approving Person is also linked to the builder, or nobody allowed approved. `JournalEntryBatchEntityServer` now refuses a save that sets or changes `ApprovedByUserID` (the Pending → Approved save, or a rewrite on an Approved batch) unless it names the signed-in user, and refuses it when there is no signed-in user. The approval Task also records the builder's Person as its creator (`CreatedByPersonID`, the builder's own People link first). That has no effect yet: the tasks app's `PreventSelfApproval` setting will refuse the builder a decision on the Task once bizapps-tasks ships it and it is enabled. Until then the send-time check above is what refuses the builder. The in-app CFO approval path is unchanged. A batch approved by a former Approval CFO is no longer sendable; cancel and rebuild it.
